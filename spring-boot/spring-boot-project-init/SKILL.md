# Spring Boot project init (Kotlin + MongoDB)

Turns a bare start.spring.io project into a running backend with the building blocks the user
picks. The layout follows `spring-boot-architecture` (feature packages, all repositories in
`repository/`, a LookupService owning each repository) — read its SKILL.md if you are unsure where
something goes. This skill only covers the one-time bootstrap; the code lives in `examples/` so
you load only what the user chose.

| Option | What gets added | Code |
|---|---|---|
| **Webserver** (always) | app class with `@EnableMongoRepositories`, `repository/`, `core/GlobalExceptionHandler`, `/public/ping` | `examples/webserver.md` |
| **Security** | JWT access + refresh tokens, `JwtAuthFilter` → `SecurityContextHolder`, `requireAuth()`/`optionalAuth()`, `SecurityConfig`, BCrypt, `User` + `RefreshToken` entities, `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `AdminGuard` | `examples/security.md` |
| **WebSocket (STOMP)** | `/ws` STOMP endpoint: `@MessageMapping` routing (the socket's `@RequestMapping`), `@Valid @Payload`, `principal.userId()`, `@MessageExceptionHandler` → `/user/queue/errors`, `SocketPublisher` for server push + presence, heartbeats; CONNECT-frame JWT auth + SEND/SUBSCRIBE destination rules when Security is chosen | `examples/websocket.md` |

## Step 1 — Inspect the project

Before asking anything, read:

- `build.gradle.kts` (or `pom.xml`): Spring Boot version, Kotlin plugins, starters already present.
- the `@SpringBootApplication` class → base package `<base>`.
- `src/main/resources/application.properties` / `.yml`.

Things to note, because they change the code you write:

- **Spring Boot 4 vs 3.** The templates target Boot 4 (Jackson 3 = `tools.jackson.*`,
  Mongo URI property `spring.mongodb.uri`). On Boot 3 use `com.fasterxml.jackson.*` and
  `spring.data.mongodb.uri`. Each example file flags the spots.
- **Starters already added.** If the user ticked `spring-boot-starter-security` on start.spring.io
  but now chooses *no* Security, every endpoint would be locked behind a generated password —
  either remove the starter or ask whether they want Security after all.
- Not a Kotlin/Gradle project, or not Mongo? Stop and tell the user; this skill assumes both.

## Step 2 — Ask what to set up

Use `AskUserQuestion` with **one multiSelect question** so the user can pick any combination:

- **Webserver only** — REST API, exception handler, Mongo wiring.
- **Security (JWT auth)** — implies Webserver.
- **WebSocket connection (STOMP)** — implies Webserver; authenticated if Security is also picked.

If something they said already answers it (e.g. "init with jwt and sockets"), skip the question.
For Security, also confirm whether they want the admin role (`AdminGuard`) — default yes.

## Step 3 — Apply, in this order

Read only the example files for the chosen options, then:

1. **Dependencies** — add the missing ones from each chosen file's "Dependencies" section. Don't
   bump versions start.spring.io pinned.
2. **Properties** — append each file's `application.properties` block. Secrets are always
   `${ENV_VAR}` placeholders, never literal values: a committed JWT secret lets anyone mint tokens
   for any user.
3. **Webserver code** (`examples/webserver.md`).
4. **Security code** (`examples/security.md`) if chosen.
5. **WebSocket code** (`examples/websocket.md`) if chosen — with Security also add `/ws` to the
   `SecurityConfig` permitAll list (auth happens in the STOMP CONNECT frame); without Security
   follow its "Without Security" section.
6. Replace `<base>` with the real base package everywhere; rename nothing else, the files
   reference each other by these names.

Write the code as given. The templates encode decisions that are easy to get subtly wrong
(token type claims, atomic refresh rotation, constant-shape login failures, STOMP destination
rules that stop clients from broadcasting to `/topic` or subscribing to foreign topics); the comments in them explain why — keep those comments, they are what stops a future edit
from "simplifying" the protection away.

## Step 4 — Verify

1. `./gradlew compileKotlin` (use the project's JDK; set `JAVA_HOME` if the default one is older
   than the toolchain). Fix errors before going on.
2. Optional smoke run if the user has Docker: `docker run --rm -d -p 27017:27017 mongo`, then
   `JWT_SECRET=<64 random chars> MONGODB_URI=mongodb://localhost:27017/app ./gradlew bootRun`
   and `curl localhost:8080/public/ping`. With Security, also register + login with curl and call
   an authenticated endpoint with the access token.
3. The default `contextLoads` test from start.spring.io needs the env vars too — mention that
   rather than deleting the test.

## Step 5 — Report

Short summary: options applied, files created (as a tree), env vars the user must set
(`JWT_SECRET` ≥ 32 bytes, `MONGODB_URI`), and next steps:

- New features → `spring-boot-architecture`.
- Socket message types / push notifications → `spring-realtime-push`.
- Offline sync endpoints → `spring-delta-sync-endpoint`.
- Before shipping endpoints → `spring-endpoint-security-check`.
- Not included on purpose: rate limiting (login is brute-forceable until bucket4j + Redis is
  added — see `spring-boot-architecture` references), email verification, password reset. The
  generic purpose-token helpers in `JwtService` are the starting point for the last two.
